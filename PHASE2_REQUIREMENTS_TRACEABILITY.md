# Phase 2 requirements traceability

Every work item and acceptance criterion from the Phase 2 brief appears below,
including the ones nothing was built for. **No requirement disappears.** A row
with `NOT IMPLEMENTED` is the point of this document as much as a row with
`AUTOMATICALLY TESTED` is — a traceability matrix that lists only what was done
is a features list.

`PHASE2_STATUS.md` holds the authoritative current status — the findings, the
twenty gates, the twenty journeys and the required documents, each in one table.
This matrix is the row-by-row evidence behind it and is kept current.

**Current as of `c5e98da`.** The closeout cycle (`66495c0`…`c5e98da`) rewrote
WI14 — which had been `NOT IMPLEMENTED` throughout — and the operator-surface
rows of WI11, WI12 and WI13, because those services now have screens. The
commerce cycle before it (`cfb654c`…`910538b`) rewrote WI8 through WI14, WI17,
WI18 and WI21. Rows that used to read `NOT IMPLEMENTED` and are now delivered
say so with the commit that delivered them; rows that are still
`NOT IMPLEMENTED` — Connect onboarding, dispute evidence, branch protection —
say that just as plainly.

Read alongside `PHASE2_IMPLEMENTATION_REPORT.md`, which explains _why_ the
delivered parts are shaped the way they are. This document says only _where_ each
requirement lives and _what evidence_ stands behind it.

## Status vocabulary

The brief requires documentation to distinguish these states. They are used here
with exactly these meanings and nothing softer:

| Status                          | Meaning                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `AUTOMATICALLY TESTED`          | Implemented, and a test in this repository fails if it stops working.                                  |
| `IMPLEMENTED`                   | Code exists and is exercised, but no test asserts this specific property.                              |
| `DB-ENFORCED`                   | The database refuses the violation, proven by a probe that attempts it.                                |
| `MOCK-ONLY`                     | Exercised only against a double. The real integration has never run.                                   |
| `EXTERNAL VERIFICATION PENDING` | Code complete; requires credentials this cycle did not have.                                           |
| `SCHEMA ONLY`                   | Tables, constraints and enums exist. No code reads or writes them.                                     |
| `SEAM ONLY`                     | An injection point exists so the feature can be added without reshaping callers. Nothing is behind it. |
| `DISABLED`                      | Deliberately impossible, and something asserts it stays impossible.                                    |
| `CARRIED`                       | Delivered in Phase 1, still standing, not extended in Phase 2.                                         |
| `NOT IMPLEMENTED`               | Nothing was built.                                                                                     |

## Evidence columns

`DB` names the migration and the constraint, index or trigger that enforces the
row's claim — `P2a` is `20260915010000_phase2_commerce_and_operations`, `P2b` is
`20260915020000_phase2_integrity_triggers`, `P2c` is
`20260915120000_verification_revoked`, `P2d` is
`20260915180000_map_version_revision`, `P2e` is
`20260915220000_event_lifecycle_integrity`, `P1` is any pre-Phase-2 migration.
`API` names the contract route id (`packages/api-contract/src/routes.js`), which
is also the only way a route can exist. `UI` names a Next.js route. It was `—`
throughout when this document was first written, and that was a finding rather
than a formatting choice; the venue and venue-map rows now name real routes,
and everything still showing `—` still has no screen.
`Tests` names the file whose failure would catch a regression.
`Manual evidence` is recorded per work item rather than per row, because in every
case it is the same sentence or absent.

**The conversion funnel is not invented.** Nothing in this system records a page
view or an anonymous browsing session, so the step everybody means by
"conversion" does not exist as data. What is reported is what _is_ recorded —
a hold taken, an order created against it, an order paid — and `funnel.missing`
names the step that cannot be counted rather than leaving a gap a reader fills
in as complete. A test asserts the naming, because an absent metric that stops
saying it is absent is an invented one.

Money comes from the ledger through the same `financeSummary` the finance screen
uses, so the two surfaces cannot disagree; everything else is counted from the
rows that are the fact. They are separate branches of the payload because
"tickets sold × face value" is not revenue, which is why the field is called
`lineValueCents`. Currencies are never added together. Every window and date
bucket is UTC and the payload says so.
